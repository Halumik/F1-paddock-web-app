# Архитектура F1 Paddock (v1.2)

**Документ описывает фактическую реализацию, а не план.**  
Составлен по коду `index.html`, `js/data.js`, `js/tracks.js`, `js/storage.js`, `js/app.js`. Приложение в браузере при составлении не запускалось; номера строк указаны на момент написания и могут смещаться при правках.  
**Актуализировано:** 20 ноября 2026 — добавлены поток демо-входа через Telegram, системная тема при `theme: null` и актуальное состояние профиля.

---

## 1. Что это за приложение

Клиентский SPA без сборщика, зависимостей и бэкенда. Открывается как статический сайт (`index.html` + файлы). Вся логика выполняется в браузере, все пользовательские данные лежат в `localStorage`. Единственный сетевой запрос — необязательная проба Jolpica API; без неё приложение полностью работает.

Данные делятся на два принципиально разных класса:

| Класс | Где живёт | Кто меняет |
|---|---|---|
| Справочный снимок сезона: этапы, сессии, пилоты, команды, результаты, схемы трасс | JS-файлы `js/data.js`, `js/tracks.js` | Разработчик правкой кода |
| Состояние пользователя: профиль, статус, отметки, друзья, прогнозы, настройки, выбранный этап | `localStorage`, ключи `f1_*` | Пользователь через интерфейс |

### 2.2. Слои и направление зависимостей

```
data.js / tracks.js   (статические справочники, read-only)
        │
        ▼
storage.js            (localStorage + нормализация + миграции + memory-fallback)
        │
        ▼
app.js: state ──► render*() ──► DOM
        │
        └──► обработчики событий ──► STORE.save*() ──► перерисовка
```

Связи не строго однонаправленные: `app.js` тоже читает `F1_DATA` напрямую (индексы `TEAM_BY_ID`, `DRIVER_BY_ID`, `RACE_BY_ID`, `app.js:11–16`), а `storage.js` использует `F1_DATA` для проверки ссылочной целостности (`isKnownRace`, `isKnownTeam`, `isKnownDriver`, `storage.js:100–118`).

### 2.3. Инициализация

`init()` (`app.js:2404`) выполняется по `DOMContentLoaded` или сразу:

1. кэш DOM-узлов (`cacheElements`);
2. проверка доступности `localStorage` (баннер);
3. построение списков пилотов и этапов;
4. `STORE.init()` — сидинг, чтение, нормализация;
5. заполнение `state` из снимка;
6. выбор этапа: сохранённый или вычисленный по дате;
7. серия `render*()`, включая `renderTheme()`/`renderProfile()`;
8. подписка обработчиков и `initSystemThemeListener()` — пока `theme === null`, смена системной темы сразу перерисовывает `data-theme`;
9. фоновая проба Jolpica;
10. через 550 мс — onboarding-модалка (`welcome`), если `onboarded !== true`;
11. интервал 60 с: обновление бейджей сессий, блока итогов и статуса (зависит от текущего времени).

Рендер императивный: строковые шаблоны → `innerHTML`, пользовательские строки проходят через `esc()` (`app.js:130–134`), текст тостов ставится через `textContent` (`app.js:2357`).

## 4. Пользовательские данные

| Сущность | Ключ | Поля | Значения по умолчанию |
|---|---|---|---|
| Профиль | `f1_profile` | `name` (2–24 символа), `team` (id команды), `onboarded` (bool), `updatedAt` (ISO), `telegram` (`@ник` или `null`), `authMethod` (`telegram-mock` или `null`), `signedInAt` (ISO или `null`) | `"Гонщик"`, `ferrari`, `false`, `null`, `null`, `null`, `null` |
| Статус просмотра | `f1_user_status` | `mode` (`live`/`recording`/`watched`), `updatedAt` | `recording`, текущее время |
| Отметки сессий | `f1_sessions` | `{ "<raceId>": { "<sessionId>": bool } }` | для `2026-brazil`: `fp1..quali = true`, `race = false` |
| Друзья | `f1_friends` | массив `{ id, name, tg, status, note, createdAt, mock }` | 3 мока: Алекс, Майя, Даня |
| Прогнозы | `f1_predictions` | `{ "<raceId>": { raceId, p1, p2, p3, savedAt } }` | нет (создаётся действием) |
| Выбранный этап | `f1_selected_race` | строка `race.id` | вычисляется по дате и сразу сохраняется |
| Настройки | `f1_prefs` | `timeMode` (`local`/`track`), `userTimezone` (строка или `null`), `theme` (`dark`/`light`/`null`) | `local`, `null` (= пояс браузера), `null` (= системная тема) |

`profile.telegram` — единственный признак авторизации: `isSignedIn()` проверяет именно его. `authMethod` и `signedInAt` описательные. Верный демо-код сразу вызывает `STORE.saveTelegramAuth(handle)`, затем шаг 3 сохраняет `name`/`team` обычным `saveProfile`. Выход вызывает `STORE.logoutProfile()`: очищаются только три Telegram-поля, `name`, `team`, `onboarded` и все остальные ключи остаются, поэтому акцент команды сохраняется в гостевом режиме.

Две разные вещи, которые легко спутать:

- **«гонка просмотрена»** — `f1_sessions[raceId].race === true`, флаг **по каждому этапу** (`app.js:195–198`);
- **«статус просмотра»** — `f1_user_status.mode`, **один на всё приложение** (`app.js:1021–1084`).

Итоги открываются только когда выполнены оба условия: гонка отмечена и режим не `recording` (`app.js:985–1019`).

## 5. Схема 1 — какие данные хранятся и как связаны

```
┌─ Справочники: js/data.js + js/tracks.js (только чтение) ─────────────────┐
│                                                                          │
│   TEAMS (11) ◄──── driver.teamId ──── DRIVERS (22)                        │
│                                            ▲                             │
│                                            │ driverId                    │
│   RACES (23) ────1:5──► SESSIONS (UTC)     └──── RESULTS (3)             │
│      │                                                                   │
│      └── race.slug ────► js/tracks.js: картинка, повороты, note           │
│                                                                          │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   │ race.id / driver.id / team.id
                                   ▼
┌─ localStorage: 7 ключей f1_* (значения — JSON-строки) ───────────────────┐
│                                                                          │
│   f1_selected_race ──► race.id                     (глобально)           │
│   f1_sessions      ──► { raceId: { sessionId: bool } }                    │
│   f1_predictions   ──► { raceId: { p1,p2,p3: driver.id, savedAt } }      │
│   f1_profile       ──► { name, team: team.id, onboarded, updatedAt,      │
│                          telegram?, authMethod?, signedInAt? }            │
│   f1_prefs         ──► { timeMode, userTimezone, theme: dark/light/null } │
│   f1_user_status   ──► { mode, updatedAt }                (глобально)     │
│   f1_friends       ──► [ { id, name, tg, status, note, … } ]              │
│                                                          (не связан       │
│                                                           с этапом)       │
└──────────────────────────────────────────────────────────────────────────┘
```

Связи по шагам:

1. **Команда → пилоты (1:N).** `driver.teamId` ссылается на `team.id`. Используется в предикторе (`<optgroup>` по командам) и в подписях подиума.
2. **Результат → пилот (N:1).** `result.driverId` ссылается на `driver.id`. Имя, номер и команда берутся из справочника при рендере.
3. **Этап → сессии (1:5).** Сессии вложены в этап; их `start`/`durationMin` определяют, идёт ли заезд и завершилась ли гонка (`app.js:178–193`).
4. **Этап → отметки (1:1 по ключу).** `f1_sessions` — карта, где внешний ключ это `race.id`, внутренние ключи — `session.id`, значения — только `true`/`false`.
5. **Этап → прогноз (1:1 по ключу).** `f1_predictions` — карта по `race.id`; `p1`, `p2`, `p3` ссылаются на `driver.id`. Именно поэтому прогнозы разных этапов не перетирают друг друга.
6. **Профиль → команда (N:1).** `profile.team` ссылается на `team.id`; валидируется при записи, при неизвестном id сбрасывается на `ferrari`.
7. **Выбранный этап → этап (N:1).** `f1_selected_race` — просто строка `race.id`; используется при загрузке и переключении.
8. **Настройки и статус — глобальные.** К этапу не привязаны. `userTimezone` определяет основной/дополнительный пояс в паре с `race.localTimezone`.
9. **Друзья — независимый список.** С этапом не связаны; текст сообщения подставляет название текущего этапа в момент клика.

Чего в схеме нет: отдельных таблиц, внешних ключей СУБД и джойнов. Все связи — это совпадение строковых `id`, а «джойн» выполняется в момент рендера через `DRIVER_BY_ID`, `TEAM_BY_ID`, `RACE_BY_ID`.

## 6. Хранение данных

### 6.1. Базовые свойства

- Хранилище: `window.localStorage` домена (например, `http://localhost:5173`), объём порядка 5 МБ.
- 7 ключей с префиксом `f1_`, все значения — JSON-строки (`storage.js:12–20`).
- Синхронизации между устройствами и браузерами нет; очистка данных сайта удаляет всё.
- При недоступном хранилище включается прозрачный memory-fallback: чтение/запись идут в объект в памяти, данные живут до перезагрузки (`storage.js:26–74`). Баннер `#storageWarning` показывается при старте (`app.js:1836–1842`).
- Тема и часть профиля читаются из `localStorage` ещё до первой отрисовки (inline-скрипты `index.html`), чтобы не было вспышки чужой темы/имени. Если `f1_prefs.theme` равен `null`, pre-paint скрипт берёт системную `prefers-color-scheme`.
- Кэш ответов API не сохраняется.
- Для проверки доступности один раз пишется и сразу удаляется служебный ключ `__f1_storage_probe__` (`storage.js:30–37`).

### 6.2. Кто и когда пишет каждый ключ

| Ключ | Сидинг | Запись пользователем |
|---|---|---|
| `f1_profile` | да | верный код (`telegram`/`authMethod`/`signedInAt`), сохранение имени и команды, выход (`telegram`/`authMethod`/`signedInAt` → `null`) |
| `f1_user_status` | да | переключатель статуса, «Я посмотрел» |
| `f1_sessions` | да, только дефолтный этап | переключение этапа (пустая карта), чекбоксы сессий, «Я посмотрел» |
| `f1_friends` | да | добавление, удаление, undo |
| `f1_predictions` | нет | сохранение/сброс прогноза |
| `f1_selected_race` | нет | при старте и при выборе этапа |
| `f1_prefs` | да | смена режима времени, пояса; первое ручное переключение темы (`null` → `dark`/`light`) |

### 6.3. Нормализация и «самолечение»

На чтении данные не принимаются на веру — каждый загрузчик приводит их к схеме:

- `normalizeProfile` — имя 2–24 символа, команда из белого списка, ISO-дата; Telegram-ник приводится к `@handle` (убираются ссылка `t.me/`, лишние `@` и недопустимые символы), проверяется формат 5–32 символов, ник демо-бота `@F1PaddockBot` отклоняется; без валидного ника профиль остаётся гостевым;
- `normalizeStatus` — строгий enum, поддержка старого строкового формата;
- `normalizeSessions` — оставляет только сессии, существующие у этапа; всё, кроме `true`, становится `false`;
- `normalizeFriends` — проверка имени/статуса, дефолтные значения, лимит 40 записей;
- `normalizePredictions` — три уникальных существующих `driver.id`, иначе запись отбрасывается;
- `normalizePrefs` — строгие enum для режима, `null` для пояса по умолчанию и `null` для темы «следовать системе»; любое другое значение темы читается как `null`.

Сессии и прогнозы после нормализации **перезаписываются** в хранилище, если нормализация что-то изменила (`storage.js:314–335`). Профиль, статус, друзья и настройки нормализуются в памяти при каждом чтении, но ключ перезаписывается только при следующем сохранении.

Битый JSON не чинится: `readJSON` вернёт `fallback`, а сидинг не перезапишет ключ, потому что он не `null`.

### 6.4. Миграции

Отдельной версии схемы нет, миграции определяются по форме данных:

| Что | Как |
|---|---|
| Старый id этапа `2026-sao-paulo` | Константа-алиас → `2026-brazil` (`storage.js:23–24`, `95–98`) |
| Плоские `f1_sessions` (без этапа) | Если ключей-этапов нет, а есть `fp1/quali/…` — оборачиваются в дефолтный этап (`storage.js:171–197`) |
| Одиночный старый прогноз | Объект с `p1..p3` превращается в карту по `raceId` (`storage.js:251–258`) |
| Старый строковый статус | `normalizeStatus` принимает и строку, и объект |
| Профиль без Telegram-полей | `normalizeProfile` оставляет `telegram/authMethod/signedInAt = null`, имя и команда сохраняются |
| Старое значение темы | `theme: "dark"` из v1.1 остаётся явным выбором; отсутствие поля или `null` означает системную тему |

### 6.5. Межвкладочная синхронизация

На `window.addEventListener('storage')` приложение перечитывает все ключи, обновляет `state`, этап, тему и перерисовывает экран. Если открыта модалка, `syncAuthStepWithProfile()` уводит её с шага профиля на шаг входа после выхода в другой вкладке и обратно — после входа. Слияния нет: работает принцип «последняя запись побеждает».

### 7.1. Пример получившейся записи

```json
{
  "2026-las-vegas": {
    "raceId": "2026-las-vegas",
    "p1": "leclerc",
    "p2": "piastri",
    "p3": "hamilton",
    "savedAt": "2026-11-18T09:14:33.518Z"
  }
}
```

| Поле | Смысл |
|---|---|
| `"2026-las-vegas"` (внешний ключ) | `race.id`, к которому привязан прогноз. Из-за этого прогнозы этапов независимы |
| `raceId` | Дублирует ключ внутри записи; нормализуется при чтении |
| `p1`, `p2`, `p3` | Идентификаторы пилотов из `F1_DATA.drivers`. Не имена, не номера, не позиции |
| `savedAt` | ISO 8601 UTC, ставится кодом в момент сохранения |

В записи нет названий команд и этапа: они вычисляются при рендере. Поэтому переименование в `data.js` сразу отражается в интерфейсе, а удаление пилота сделает старый прогноз невалидным — при следующей загрузке он будет отброшен.

### 7.2. Соседние операции

| Действие | Что происходит |
|---|---|
| «Изменить» | `predictionEditing = true`, форма заполняется сохранёнными значениями (`app.js:1700`) |
| «Сбросить» | `clearPrediction` удаляет запись этапа; если карта опустела — удаляется весь ключ (`app.js:1710`, `storage.js:385–390`) |
| Переключение этапа | `selectRace` сохраняет новый `raceId` и перерисовывает прогноз уже для него (`app.js:605–629`) |
| F5 | `STORE.init()` → `normalizePredictions()` → карточка восстанавливается (`storage.js:314–335`, `app.js:2415`) |

Особенности реализации:

- `MOCK_TELEGRAM_CODE` и `TELEGRAM_BOT_HANDLE` объявлены только в `app.js`; код не пишется в `localStorage` и не логируется.
- Шаг `welcome` показывается только при `onboarded !== true`; позже гостевая кнопка сразу открывает `telegram`.
- Степпер (`#authStepper`) виден на шагах `telegram`, `code` и на шаге `profile` после верного кода. В режиме `edit` для уже авторизованного пользователя он скрыт: это обычный редактор профиля.
- При выходе модалка закрывается, шапка возвращается в гостевой вид, акцент последней команды остаётся.
- Реального Bot API нет: `handleTelegramSubmit` только переводит на шаг кода. Сетевой слой не затрагивается, поэтому офлайн-поведение не меняется.

## 8. Валидация и обязательность

| Данные | Обязательное условие | Поведение при нарушении |
|---|---|---|
| Профиль, имя | 2–24 символа | ошибка в модалке, сохранение блокируется; при чтении — `"Гонщик"` |
| Профиль, команда | Один из 11 id | при чтении — `ferrari` |
| Профиль, Telegram | `@` + 5–32 символа, латиница/цифры/`_`, не `@F1PaddockBot` | ошибка формы; при чтении ник отбрасывается, профиль гостевой |
| Код подтверждения | ровно 4 цифры, `1234` в демо | ошибка под полем, сессия не создаётся |
| Статус | `live`/`recording`/`watched` | при чтении — `recording` |
| Друг, имя | ≥ 2 символов | ошибка формы |
| Друг, `tg` | ≥ 3 символов, латиница/цифры/`_`, уникален | ошибка формы |
| Друг, статус | один из трёх | ошибка формы |
| Прогноз | 3 заполненных, разных, существующих пилота | ошибка формы/тоста; запись не создаётся |
| Этап в прогнозе | известный `race.id` | при чтении — перенос на `defaultRaceId` |
| Выбранный этап | известный `race.id` | сохранение игнорируется |
| `timeMode`, `theme` | строгий enum; `theme: null` допустим | при чтении — `local`, `null` (системная тема) |
| `userTimezone` | строка или `null` | список поясов проверяется только в UI |

Общая модель: **UI проверяет ввод, хранилище повторно проверяет всё при чтении и записи**. Никакое значение из `localStorage` не считается доверенным.

## 9. Ограничения текущей реализации

### Платформа и хранение

- Только браузер и только этот домен: нет бэкенда, реальных аккаунтов, синхронизации между устройствами. «Вход через Telegram» — локальная демо-сессия.
- Около 5 МБ, привязано к браузеру; очистка данных сайта стирает профиль, друзей, прогнозы и настройки.
- Нет версии схемы и формальных миграций: определение «старый/новый формат» эвристическое. Добавление новых полей придётся делать такими же эвристиками.
- Нет экспорта/импорта состояния — резервную копию сделать нельзя.
- Memory-fallback живёт до перезагрузки; предупреждение показывается только при старте, а не в момент, когда хранилище отказало позже.
- Слияние между вкладками отсутствует: последняя запись перетирает предыдущую.
- Битый JSON не восстанавливается автоматически (кроме `f1_sessions` и `f1_predictions`, которые перезаписываются после нормализации).

### Данные

- Справочник — статический снимок. Новые результаты и переносы гонок обновляются только правкой `js/data.js`.
- API-проба не влияет на расписание и результаты; она читает первый элемент `MRData.RaceTable.Races`, то есть подтверждает сезон/раунд таблицы, а не «текущий раунд» в буквальном смысле.
- Ответ API не кэшируется, офлайн-поведение полностью зависит от локального снимка.
- Лимит друзей — 40 записей; превышение обрезается молча (`storage.js:220`).
- Имя профиля обрезается до 24 символов молча (`app.js:1901`).
- При изменении состава сессий в `data.js` старые флаги неизвестных сессий исчезают; при удалении пилота его прогнозы отбрасываются.
- `getTeam()` и `getRace()` при неизвестном id возвращают первый элемент справочника (`app.js:140–150`), то есть ошибка данных может выглядеть как «Ferrari»/«Австралия», а не как пустое состояние.

### Поведение

- Стартовый этап вычисляется по текущей дате (`app.js:204–218`): этап, чья гонка началась не позже 4 дней назад, иначе ближайший будущий. Поведение первого запуска зависит от дня, а статическая разметка `index.html` при этом свёрстана под Сан-Паулу.
- Статус просмотра глобальный, отметка гонки — по этапу; итоги открываются только при комбинации «отмечено + не `recording`».
- Отметки сессий и прогнозы разрешены для любых этапов, включая будущие и уже завершённые.
- `.ics` выгружает все 5 сессий выбранного этапа независимо от того, прошли они или нет; время в UTC.
- Нет автоматического обновления результатов после завершения будущих гонок и нет автоотметки «посмотрел».
- Запасной вариант ссылки `t.me/share/url` практически недостижим: при отсутствующем `tg` хранилище подставляет `@friend`, а UI не даёт сохранить друга без ника.
- Интерфейс и форматы дат — только русские; мультиязычности нет.

### Безопасность

- Spoiler Shield — клиентская защита: разметка подиума создаётся в DOM и при закрытом блоке скрывается визуально, через `inert` и `aria-hidden` (`app.js:947–1019`). Это защита от случайного спойлера, а не граница безопасности.
- Всё содержимое `localStorage` доступно любому скрипту на этом origin; CSP в проекте не задан.
- Пользовательские строки экранируются через `esc()`; текст тостов ставится через `textContent`; внешние ссылки открываются с `rel="noopener noreferrer"`.
- Реальной авторизации нет: демо-код `1234` проверяется в браузере, ник Telegram не подтверждается, сообщения не отправляются. `f1_profile.telegram` — локальная запись, а не сессия сервера.
- Системная тема — только `prefers-color-scheme`; при `theme: null` приложение следует ОС, ручной выбор хранится в `f1_prefs`.

### Поддерживаемость

- Нет сборки, линтера и автотестов; проверка ручная.
- `js/app.js` — один IIFE примерно на 2,6 тыс. строк: состояние, вход, рендер и обработчики в одном файле, полная перерисовка блоков через `innerHTML`.
- Состояние дублируется: `state` в памяти и те же данные в `localStorage`; истина — хранилище, `state` обновляется после каждой записи.
- Нет полифиллов: используются `AbortController`, `Intl`, `TextEncoder`, `inert` (последний — с fallback), современный CSS.

После актуализации PRD 20 ноября 2026 расхождений по стартовому этапу, подписям статусов, Telegram-ссылке, таймауту API, ключам хранилища и демо-входу нет. Остаются продуктовые неоднозначности:

- Spoiler Shield — клиентская UX-защита, а не security-boundary.
